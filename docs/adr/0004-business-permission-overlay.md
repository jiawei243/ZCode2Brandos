# ADR-0004: 业务级权限叠加在现有 permission 体系之上，不替换内核语义

- 状态：已接受（2026-09-21）
- 关联：ADR-0002、专利产品规划 §5.2 #11

## 背景

WBrand 的 permission mode 是开发者语义（"允许执行这条命令吗"）。专利机构的用户需要业务级门控：能否提交案件、能否修改申请人术语表、能否查看未过审方案、能否接手他人会话。品牌版计划提出"权限语义整个换掉"。

## 决策

- **内核 permission mode 保持不动**。在其上新增 policy 服务（属 ADR-0002 的组织/案件域）：角色（代理人/复核人/流程/管理员）→ 业务动作的映射，policy 判定结果投影为工具策略与会话访问控制。
- 复核协作（查看/接手成员会话）复用已核实的 `conversation-share` 服务，叠加角色约束。
- 工具级批准对业务用户透明化：由 policy 自动处理，不再逐条弹给业务用户。

## 理由（决策树 1–3 不可行的部分）

- 业务角色→动作映射是业务状态，扩展点承载不了"谁能看哪类案件"。
- 但"替换 permission mode 语义"是改内核：mode 定义与判定分散在 `apps/wbrand-cli/packages/core`（permission/service）与协议中，改动即上游分叉，且会破坏桌面/CLI/远程三形态的一致行为。叠加层能表达全部业务门控，因此不替换。

## 后果

- 存在两层权限（内核工具层 + 业务 policy 层），必须写清组合语义：policy 是"业务准入"，内核是"工具执行准入"，二者与而非或。
- 审计要求（谁批准了提交）落在 policy 服务 + hooks 落库（规划 §5.2 #13）。
